我们在讲解 Map 时曾提到过，使用 Map 的一大误区就是并发的去读写 Map ，那么实际场景中我们有时确实需要这个数据结构，那么我们怎么办呢？

通过前面的学习，大家想必有了思路，可以自己实现一个可以并发读写的 Map ，比如可以使用 Mutex ，在读写时上锁，但是效率过低。我们还学习过 RWMutex ，但是我们说过 RWMutex 读锁存在时会阻碍写，总的来说就是锁是万恶之源，有了它安全但是效率就会低下。

go实现了 sync.map 应对了 Map 并发场景，接下来我们就从使用、原理、以及一些流程下讲解下 sync.map 。

使用

  • Store 方法用于向 sync.Map 中添加或更新键值对。
  • Load 方法用于从 sync.Map 中获取指定键的值。如果键存在，则返回对应的值和 true；否则返回零值和 false。
  • Delete 方法用于从 sync.Map 中移除指定的键。
  • Range 方法用于遍历 sync.Map 中的所有键值对。传递给它的函数接收两个参数：键和值。如果该函数返回 false，则停止遍历；如果返回 true，则继续遍历下一个元素。

实现原理

数据结构

map

  • read：无锁化的只读 map，实际类型为 readOnly；
  • dirty：加锁处理的读写 map；
  • misses：记录访问 read 的失效次数，累计达到阈值时，会进行 read map/dirty map 的更新轮换；
  • mu：一把互斥锁，实现 dirty 和 misses 的并发管理.

可以看到 sync.Map 的特点是冗余了两份 map： read map 和 dirty map，核心思路实际就是首先基于无锁操作访问 read map；倘若 read map 不存在该 key，则加锁并使用 dirty map 兜底， read map 和 dirty map 之间会交替轮换更新。

entry

value 统一采用 unsafe.Pointer 的形式进行存储，通过 entry.p 的指针进行链接.

entry.p 的指向分为三种情况：

  • 存活态：正常指向元素；
  • 软删除态：指向 nil； nil 态表示软删除， read map 和 dirty map 底层的 map 结构仍存在 key-entry 对，但在逻辑上该 key-entry 对已经被删除，因此无法被用户查询到；
  • 硬删除态：指向固定的全局变量 expunged 。 expunged 态表示硬删除， dirty map 中已不存在该 key-entry 对。

readOnly

sync.Map 中的只读 map：read 内部包含两个成员属性：

  • m：真正意义上的 read map，实现从 key 到 entry 的映射；
  • amended：标识 read map 中的 key-entry 对是否存在缺失，需要通过 dirty map 兜底.

方法实现

接下来都会先说明方法的大体思路，随后通过详解源码的方式来探究 sync.Map 的读写实现。

读：sync.Map.Load()

基本思路如下：

  • 1. 首先会访问 read map ，判断 read map 是否在含有 key 的同时 amended 缺失标识为 false，
    • 1.1 如果此时含有 key 的同时 amended 缺失标识为 false，就说明 read map 数据不缺失且 key 也存在，即可直接访问 read map ，经过 key 是否存在和 entry.p 状态来返回值。
    • 1.2 如果前者不成立，则会上锁，同时重新访问 read map ，判断 read map 是否在含有 key 的同时 amended 缺失标识为 false 作一个双重检查，以防锁前 read map 已经更新且符合条件
      • 如果此时含有 key 的同时 amended 缺失标识为 false，就说明 read map 在刚刚时间被更新，直接进入1.1和1.2判断
      • 如果前者依旧不成立，则会访问 dirty ，同时给 misses 次数加一。进入类似1.1和1.2的判断。

其他问题

为什么为什么我们读写流程中 missLocked 将 dirty 置为 nil，在写流程中又将 read map 的数据重新给了 dirty，这样不是多此一举么？

首先我们要明确二者的目的：

  • missLocked 将 dirty 置为 nil：是因为我们将 dirty 数据全同步给了 read ，留下数据已经没用了。
  • 写流程中又将 read map 的数据重新给了 dirty：这个复制是经过筛选的，重新给 dirty 时会将删除的 key 剔除。

再者我们从源码分析也可得出 sync.map 实际上是比较适合于读多写少的情况，它提供了一个 read map 通过 for + CAS 保证了全程无锁，也有一个读写都使用 Mutex 的 dirty map。

entry 的状态有什么用？为什么还得需要expunged？

首先需要明确，无论是软删除( nil)还是硬删除( expunged),都表示在逻辑意义上 key-entry 对已经从 sync.Map 中删除， nil 和 expunged 的区别在于：

  • 软删除态（ nil）： read map 和 dirty map 在物理上仍保有该 key-entry 对，因此倘若此时需要对该 entry 执行写操作，可以直接 CAS 操作；
  • 硬删除态（ expunged）： dirty map 中已经没有该 key-entry 对，倘若执行写操作，必须加锁（ dirty map 必须含有全量 key-entry 对数据）.

主要是为了优化 dirtyLocked 前，针对同一个 key 先删后写的场景。
