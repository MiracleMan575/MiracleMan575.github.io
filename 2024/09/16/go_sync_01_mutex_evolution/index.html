Mutex进化史

如果是你设计Mutex，你会怎么设计呢？

最简单的方法就是直接使用一个flag标志位，0代表未被持有，1代表已被持有，实际上初代Mutex就是这样做的。

第一版Mutex：互斥锁的诞生

数据结构

  • key：是一个 flag，用来标识这个排外锁是否被某个 goroutine 所持有，如果 key大于等于 1，说明这个排外锁已经被持有。
    • 0：锁未被持有
    • 1：锁被持有，没有等待者
    • n：锁被持有，还有n-1个等待者。
  • sema：是个信号量变量，用来控制等待 goroutine 的阻塞休眠和唤醒。

很显然，锁被持有的优先级是先来先得，这样看起来貌似很公平，但如果我们能够把锁交给正在占

用 CPU 时间片的 goroutine 的话，那就不需要做上下文的切换，从而提高并发性能。

第二版 Mutex : 给新人机会

第二版针对与第一版的缺陷做出了对应修改，核心思想是“给新人机会”。

数据结构

state字段包含了多个含义：

  • 最低位mutexLocked：锁是否被持有。
  • 第二位mutexWoken：是由有唤醒的goroutine。
  • 剩余高位mutexWaiters：等待此锁的goroutine数量。

相对于初版的设计，这次的改动主要就是，新来的 goroutine 也有机会先获取到锁，甚至一个 goroutine 可能连续获取到锁，打破了先来先得的逻辑。

虽然这一版的 Mutex 已经给新来请求锁的 goroutine 一些机会，让它参与竞争，没有空闲的锁或者竞争失败才加入到等待队列中。但是其实还可以进一步优化。我们接着往下看。

第三版Mutex : 多给些机会

对于有些时候果新来的 goroutine 或者是被唤醒的 goroutine 可能获取不到锁，那就会直接休眠。但可能下一瞬间就可能获取到锁，针对这种情况，第三版加入了锁自旋。

新来的 goroutine 或者是被唤醒的 goroutine 首次获取不到锁，就进行自旋，在尝试一定的自旋次数后，再执行原来的逻辑。

因为临界区的代码耗时很短，锁很快就能释放，而抢夺锁的 goroutine 不用通过休眠唤醒方式等待调度，直接 spin 几次，可能就获得了锁。

针对 goroutine 加锁时发现锁已被抢占的这种情形，此时摆在面前的策略有如下两种：

  • 阻塞/唤醒：将当前 goroutine 阻塞挂起，直到锁被释放后，以回调的方式将阻塞 goroutine 重新唤醒，进行锁争夺；
  • 自旋 + CAS：基于自旋结合 CAS 的方式，重复校验锁的状态并尝试获取锁，始终把主动权握在手中.

优势劣势适用场景阻塞/唤醒精准打击，不浪费 CPU 时间片需要挂起协程，进行上下文切换，操作较重并发竞争激烈的场景自旋+CAS无需阻塞协程，短期来看操作较轻长时间争而不得，会浪费 CPU 时间片并发竞争强度低的场景

sync.Mutex 结合两种方案的使用场景，制定了一个锁升级的过程，反映了面对并发环境通过持续试探逐渐由乐观逐渐转为悲观的态度，具体方案如下：

  • 首先保持乐观，goroutine 采用自旋 + CAS 的策略争夺锁；
  • 尝试持续受挫达到一定条件后，判定当前过于激烈，则由自旋转为阻塞/挂起模式.

具体条件可以查看源码，主要有这几个：

  • 自旋累计达到 4 次仍未取得战果；
  • CPU 单核或仅有单个 P 调度器；（此时自旋，其他 goroutine 根本没机会释放锁，自旋纯属空转）；
  • 当前 P 的执行队列中仍有待执行的 G. （避免因自旋影响到 GMP 调度效率）.

第四版：解决饥饿

随着优化，Mutex 应对高并发争抢锁的场景也更加公平。但是有没有想过，因为新来的 goroutine 也参与竞争，有可能每次都会被新来的 goroutine 抢到获取锁的机会，在极端情况下，等待中的 goroutine 可能会一直获取不到锁，这就是 饥饿问题。

为了解决这个问题，go的开发者们对state字段添加了新的标记。

  • mutexLocked: 表示锁被占用的标志位。
  • mutexWoken: 表示有等待者被唤醒的标志位。
  • mutexStarving: 表示锁处于饥饿模式的标志位。
  • mutexWaiterShift: 用于计算等待者的数量，通过右移操作从 state 中提取等待者数量。
  • starvationThresholdNs: 饥饿模式的阈值时间，单位为纳秒，表示如果一个 goroutine 等待超过这个时间，则进入饥饿模式。

Mutex 最重要的变化，就是增加饥饿模式。一旦等待者等待的时间超过了这个阈值，Mutex 的处理就有可能进入饥饿模式，优先让等待者先获取到锁，新来的同学主动谦让一下，给老同志一些机会。

正常模式下，waiter 都是进入先入先出队列，被唤醒的 waiter 并不会直接持有锁，而是要和新来的goroutine 进行竞争。新来的 goroutine 有先天的优势，它们正在 CPU 中运行，或许它们的数量还不少，所以，在高并发情况下，被唤醒的 waiter 可能获取不到锁，它会被插入到队列的前面。如果 waiter 获取不到锁的时间超过阈值 1 毫秒，这个 Mutex 就进入到了饥饿模式。

在饥饿模式下，Mutex 的拥有者将直接把锁交给队列最前面的 waiter。新来的 goroutine不会尝试获取锁，即使看起来锁没有被持有，它也不会去抢，也不会 spin，它会加入到等待队列的尾部。

如果拥有 Mutex 的 waiter 发现下面两种情况的其中之一，它就会把这个 Mutex 转换成正常模式:

  • 此 waiter 已经是队列中的最后一个 waiter 了，没有其它的等待锁的 goroutine 了；
  • 此 waiter 的等待时间小于 1 毫秒。

正常模式拥有更好的性能，因为即使有等待抢锁的 waiter，goroutine 也可以连续多次获取到锁。饥饿模式是对公平性和性能的一种平衡，它避免了某些 goroutine 长时间的等待锁。在饥饿模式下，优先对待的是那些一直在等待的 waiter。

常见的 4 种错误场景

Lock/Unlock 不是成对出现

我们实际开发中，一般是粗心导致的，比如

  • 代码中有太多的 if-else 分支，可能在某个分支中漏写了 Unlock；
  • 在重构的时候把 Unlock 给删除了；
  • Unlock 误写成了 Lock。

但是我们运行时会直接panic，所以问题还是比较

Copy 已使用的 Mutex

我们前面讲到了state 字段记录Mutex的状态，当我们复制了Mutex，使用时发现这个初始的Mutex被加锁了，当然也可能是没有加锁的，但在高并发的前提下，你无法预测当你复制时，Mutex的状态。

很显然你明白，但是有些时候还是会出现使用问题：比如你将Mutex嵌入了其他结构体，然后将这个结构体直接传递给了函数，而不是通过指针。

Go 在运行时，有死锁的检查机制 checkdead() 方法，程序运行的时候，死锁检查机制能够发现这种死锁情况并输出错误信息。

重入

首先区分什么是可重入锁，什么是不可重入锁：

  • 可重入锁：当一个线程已经持有了某个可重入锁，并尝试再次获取这个锁时，该线程能够成功获得锁而不被阻塞也不会造成死锁。
  • 不可重入锁不允许同一个线程多次获取同一把锁，如果一个线程试图再次获取它已经持有的锁，则该线程会被阻塞或导致死锁。

Mutex 不是可重入的锁。

前面我们探索过Mutex的实现，很明显并没有记录谁拥有锁，也没有计数器。理论上，任何goroutine都可以去随意Unlock锁。我们之前也提到过，Mutex的state的最低位 mutexLocked 表示锁是否被占用，也就代表他只有两个值，0空闲和1占用，无法充当计数器。

我们怎么样实现可重入锁呢？

  • goroutine id：通过 runtime.Stack 方法获取栈帧信息，栈帧信息里包含 goroutine id。
  • token：调用者自己提供一个 token，获取锁的时候把这个 token 传入，释放锁的时候也需要把这个 token 传入，通过用户传入的 token 替换 goroutine id。

死锁

学过OS都知道死锁是什么，就是两个或者两个以上的进程因为资源相互等待，A需要ab两样资源，B也需要ab两样资源，但现在A拥有a，B拥有b，两者相互等待。举个例子就是你要找工作需要证明你有1年工作经验，因为你没有经验所以不要你，但是你需要工作才能有工作经验。那这样下去用人单位招不到人，你同时也找不到工作了。

OS讲过死锁产生的必要条件：

  • 互斥： 至少一个资源是被排他性独享的，其他线程必须处于等待状态，直到资源被释放。
  • 持有和等待：goroutine 持有一个资源，并且还在请求其它 goroutine 持有的资源。
  • 不可剥夺：资源只能由持有它的 goroutine 来释放。
  • 环路等待：存在一组等待进程，A需要a，但a有B持有，同时B需要b，但由C持有，C需要c，但由A持有，这就形成了死结。

Mutex的提高和用途

TryLock

如果你了解过MySQL，并恰巧知道MySQL的锁，你已经对Try不陌生。 TryLock 尝试获取锁。当然go官方标准库中并未实现 TryLock(),但在实际开发中我们为了避免同时多个 goroutine 并发修改数据也会使用 TryLock。他的原理也很简单：就是尝试去占用锁，如果锁未被其他goroutine占用，则直接持有这把锁，并返回true；如果这把锁已经被其他goroutine占用或正在准备交给被唤醒的goroutine上，那就直接返回false。
