在 Docker4——尝试部署 章节中我们留下了一个对于Kibana的部署，因为针对于Kibana容器，是需要与ES容器进行网络连接的。网络互通的关键在于“打通”容器内外的网络，docker是怎么做的呢？

网络模式

Docker提供了三种网络模式，分别是 null、 host 和 bridge。接下来我们将通过实验或者一些简单图的方式尝试向你说明白这种网络模式之间的不同。

为了便于说明，我们将之前所有容器停止并删除，同时将镜像也一并删除。

接下来我们使用 ip addr 命令查看主机系统中所有的网络接口及其配置的 IP 地址信息。

bridge

桥接模式，它有点类似现实世界里的交换机、路由器，只不过是由软件虚拟出来的，容器和宿主机再通过虚拟网卡接入这个网桥，那么它们之间也就可以正常的收发网络数据包了。

这里我们新建容器，并在本机和容器内分别使用 ip addr 命令。

我们可以惊喜的发现nginx01容器内输出信息内有 14: eth0@if15， ip 为 172.17.0.2，而本机对应也多了一条输出信息 15: vethd75b5b4@if14，因为本机 docker0 的ip为 172.17.0.1，跟 172.17.0.2 在同一网段，他们肯定可以ping通，也就是容器和本机是网络互通的。我们也可以尝试命令去ping一下发现互通。

接下来我们尝试创建nignx02虚拟机并将其启动，同样进行上述操作。

docker run -d –rm –name nginx02 nginx:alpine

docker exec -it nginx02 ip addr

ip addr

由此得出nginx02和本机也是互通的，那nginx01和nginx02呢？

不错，他们也是互通的，想必大家看到这一定明白了为什么说桥接模式像路由器。如下图，当我们由nginx01发送数据给nignx02时，实际是通过了 docker0 转发的，所以 docker0 像桥梁一样承担起了通信的工作，这也就是为什么叫桥接模式了。Docker中所有网络接口都是虚拟的，所以转发效率非常高。

接下来我们移除nginx01，这里因为启动命令加了 --rm，所以直接stop容器即可删除，发现对应网桥消失了。

但是在实际场景中，因为docker桥接对于容器的ip分配是随机的，而我们又无法预测，我们希望使用容器名可以ping通，但是是有问题的。

这里需要说一下，如果想直接通过容器名来实现互通，有一项比较旧的技术可以实现， --link，可以自己尝试下，这个是单向的，原理就是在hosts文件中加入了容器名和ip的映射。但这有许多缺点：

  • 使用“–link”会增加容器启动命令的复杂度，尤其是在需要链接多个容器时，这可能导致难以管理和维护。
  • 默认情况下，用户自定义网络更加安全，因为它不会自动暴露所有端口给其他容器，除非显式地配置了。
  • 在服务发生变动时，比如服务重启或扩展，需要手动管理链接。

none

最简单的模式，也就是没有网络，但允许其他的网络插件来自定义网络连接。

可以发现只有本机环回地址。

host

主机模式，直接使用宿主机网络，相当于去掉了容器的网络隔离（其他隔离依然保留），所有的容器会共享宿主机的IP地址和网卡。这种模式没有中间层，自然通信效率高，但缺少了隔离，运行太多的容器也容易导致端口冲突。

可以发现和主机的网络设置相同。
