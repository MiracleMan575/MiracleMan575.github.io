你的某个同事可能会跳出来，说：”为什么不写COUNT(1)，你要知道，COUNT(1)肯定要比COUNT(*)效率高，这个SQL要优化，要改掉！“

你问原因时，对方解释道，因为 SELECT * 和 SELECT 1 效率是不同的！

千万不要被误导！

实际上COUNT(1)和COUNT(*)效率几乎一样！

COUNT(1)

count(1)的执行过程用到了 count() 聚合函数 ，该函数的作用是 统计符合查询条件的记录中，函数指定的参数不为 NULL 的记录有多少个。

我们如果这么写

实际意义就是统计了  user表中，1 这个表达式不为 NULL 的记录 到底有多少个，而 1 就是单纯的数字，它永远都不是NULL ，所以这条语句实际就统计了表中有多少条记录。

我们尝试使用EXPLAIN看一下执行计划，会较为清晰的发现

使用了主键索引，这是因为该表创建时使用了主键索引。

那如果我们将 user 表 drop 掉，重新创建user而不建立索引时，你会发现，他并不会走索引。

如果我们建立了二级索引，即表里有二级索引时，InnoDB 循环遍历的对象就是二级索引了；这是因为相同数量的二级索引记录可以比聚簇索引记录占用更少的存储空间，所以二级索引树比聚簇索引树小，这样遍历二级索引的 I/O 成本比遍历聚簇索引的 I/O 成本小，因此「优化器」优先选择的是二级索引。

COUNT(*)

看到 * 这个字符的时候，是不是大家觉得是读取记录中的所有字段值？

MySQL会将其转换为COUNT(0)，这本质和COUNT(1)没什么区别。

COUNT(column_name)

这是效率最差的，通过前面的讲解，想必你肯定知道了这个语句的意思为：统计了  user表中，column_name不为 NULL 的记录 到底有多少个，这个必须进行全表扫描。

小结

count(1)、 count(*)、 count(主键字段)在执行的时候，如果表里存在二级索引，优化器就会选择二级索引进行扫描。

所以，如果要执行 count(1)、 count(*)、 count(主键字段) 时，尽量在数据表上建立二级索引，这样优化器会自动采用 key_len 最小的二级索引进行扫描，相比于扫描主键索引效率会高一些。

再来，就是不要使用 count(字段) 来统计记录个数，因为它的效率是最差的，会采用全表扫描的方式来统计。如果你非要统计表中该字段不为 NULL 的记录个数，建议给这个字段建立一个二级索引。

为什么要通过COUNT统计个数？

你可能会好奇，为什么 count 函数需要通过遍历的方式来统计记录个数？

我前面讲的案例都是基于 Innodb 存储引擎来说明的，但是在 MyISAM 存储引擎里，执行 count 函数的方式是不一样的，通常在没有任何查询条件下的 count(*)，MyISAM 的查询速度要明显快于 InnoDB。

使用 MyISAM 引擎时，执行 count 函数只需要 O(1)复杂度，这是因为每张 MyISAM 的数据表都有一个 meta 信息有存储了row_count值，由表级锁保证一致性，所以直接读取 row_count 值就是 count 函数的执行结果。

而 InnoDB 存储引擎是支持事务的，同一个时刻的多个查询，由于多版本并发控制（MVCC）的原因，InnoDB 表“应该返回多少行”也是不确定的，所以无法像 MyISAM一样，只维护一个 row_count 变量。
