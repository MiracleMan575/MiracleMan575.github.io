前置知识

数据结构：B树和B+树

我们先来看一对树

B树

B树，就是Balance Tree，也就是平衡树，B树实质是一棵(N-1)-N查找树，N叫做B树的阶，B树延续了二三查找树的本质，将其结点的key进行拓展，我们知道一个结点能够存储更多的key，那么这棵树的高度也就越低，进而查找效率就会高。这样解释有些苍白，我们直接看图，假设表数据如下图左侧所示，那么B树就是这个样子：

B+树

B+树是在特定的场景下对B树做了优化，像咱们B树是key和data都存储在一块，这样无疑增加了内存消耗。而B+树数据是存储在当前树的叶子结点上，非叶子结点存储的只是相应的key。同样我们直接看下图：

B+ 树用于数据库索引有 3 大优势。

  1. B+ 树的高度和二叉树之类的比起来更低，树的高度代表了查询的耗时，所以 查询性能更好。
  2. B+ 树的叶子节点都被串联起来了，适合 范围查询。
  3. B+ 树的非叶子节点没有存放数据，所以 适合放入内存中。

索引分类

MySQL索引根据划分规则不同可以分成以下几种：

聚簇索引和非聚簇索引：聚簇索引叶子节点存储数据；非聚簇索引反之。

覆盖索引：某个索引包含某个查询的所有列。

唯一索引：索引的值必须是唯一的。

前缀索引：索引的某个列，只包含该列值的前一部分

组合索引：多个列组成

全文索引：支持文本模糊查询

哈希索引：使用哈希算法的索引；InnoDB不支持该索引

对于联合索引，查询时是使用最左匹配原则的，也就是你有三个索引ABC，A是绝对有序的，在A确定的情况下，B才是有序的，同样在AB都确定的情况下，C才是有序的。这也就不难理解为什么当你不按照索引的顺序使用联合索引时，MySQL会不走索引的情况了。

索引的代价

索引并不是没有代价的，它会消耗很多的系统资源。

  1. 索引本身需要存储起来，消耗磁盘空间。
  2. 在运行的时候，索引会被加载到内存里面，消耗内存空间。
  3. 在增删改的时候，数据库还需要同步维护索引，引入额外的消耗。

MySQL 为什么使用 B+ 树？

与 B+ 树相比，平衡二叉树、红黑树在同等数据量下，高度更高，性能更差，而且它们会频繁执行再平衡过程，来保证树形结构平衡。

与 B+ 树相比，跳表在极端情况下会退化为链表， 平衡性差，而数据库查询需要一个可预期的查询时间，并且跳表需要更多的内存。

与 B+ 树相比，B 树的数据存储在全部节点中， 对范围查询不友好。非叶子节点存储了数据， 导致内存中难以放下全部非叶子节点。如果内存放不下非叶子节点，那么就意味着查询非叶子节点的时候都需要磁盘 IO。

什么情况下不走索引反而更快？

  1. 小表查询：对于某张表只有几十行或者几行数据，MySQL会进行全表扫描，要比索引更快。
  2. 读取大部分或所有行：当查询返回表中绝大多数部分数据时，使用所以索引可能会耗时更多。因为数据库必须跳回主数据页以读取完整记录。
  3. 低选择性索引：比如布尔型，依赖索引会产生不必要的开销。
  4. 频繁更新的表：频繁写的表索引维护成本很高，尤其是频繁更新索引列时，会加重读写负担。
  5. 负责查询的优化选择：对于负责的多表查询，优化器有时会选择不走某个索引来提交联接或计算效率
  6. 数据分布与优化器误判：某些情况下，如果索引错误的估计数据分布或行数，可以手动金庸或者提示优化器使用不同策略提升性能。
